The problem

A public hospital with eight specialties still runs scheduling by phone. Cardiology and oncology waitlists regularly exceed six weeks.

Our initial interpretation, before we found the full brief, assumed a single private clinic and one specialist. The real scope is one pilot specialty — cardiology — inside a much larger hospital system, with a meaningful share of patients who aren't digitally reachable at all.

How we applied the pillars

Not the theory — what actually happened.

G

Governance

We overruled an AI suggestion to let urgent cases jump the waitlist — real clinics absorb emergencies as same-day delays, not queue reordering, so we locked in strict FIFO.EvidenceBR-006 and the resolved decision in PS-001 section 14

A

Alignment

UX built the journey maps and working prototype; BA/QA folded every open decision into the Product Spec — each round of feedback updated both before the next build pass.EvidenceOpen review findings became questions for the Product Owner; the answers were applied in spec v2.4 and the QA spec

Q

Quality

We caught our own prototype contradicting our own business rule — a decline was auto-cascading to the next patient when the spec required a separate staff action. Fixed before it reached the team.EvidenceReviews also flagged "first in line" contradicting the skip rule; fixed in v2.3

L

Living Agility

A missed Confluence brief, found mid-hackathon, reframed our entire scope — from a single private clinic to one pilot specialty inside an 8-specialty public hospital — and the spec was rewritten to match, not the other way around.EvidencePS-001 v0.4 realigned as v2.0; scope narrowed again in v2.2

A

Adaptability

We kept the prototype one HTML page with internal tabs instead of multiple pages, specifically because our dev needed to build fast — calibrated to the week's real constraint, not gold-plated.EvidenceQA test spec capped at 20 cases; the suite automates only what can run on today's build

What didn't go as expected

1

A brief we hadn't seen

On day 3 we discovered a Confluence doc with the full, real problem statement — our scope had been an assumption, not a fact, for two days.

2

A rule we'd built wrong

Our own prototype auto-advanced the waitlist on a decline — directly contradicting a business rule we ourselves had written. Caught by re-reading the spec against the build.

3

A bug only the script found

Writing the literal demo script — not just clicking around — surfaced a queue-ordering bug no one had noticed in casual testing.

Still open
Spec status. v2.0 called itself "Ready with Minor Refinement"; the review said "Requires Refinement". We corrected it, and v2.4 still carries open confirmations.
Telephone path. It is specified, but not built yet: 0 of 30 tasks done, so 11 automated tests wait for it.

The spec as a living record

What changed between day 1 and today — and why that's the point.

Day 1

  • Single private clinic, one specialist — assumed
  • Patients see a live waitlist position
  • Patients can be removed from the list
  • Digital-only — no telephone path considered

Today

  • One pilot specialty in an 8-specialty hospital — confirmed
  • Position display deferred — explicitly out of this iteration
  • Removal deferred — explicitly out of this iteration
  • Telephone path is a primary path, not an edge case
